# Booking Service — Java Pet Project

Практический проект для Java-разработчиков, построенный вокруг реального микросервиса бронирования.

Сервис работает в связке с внешним Catalog Service через RabbitMQ — как в настоящей распределённой системе. Задачи спроектированы так, чтобы каждая затрагивала конкретный паттерн или проблему, с которыми сталкиваются на реальных проектах.

## Стек

- **Java 21**, **Spring Boot 3**
- **Spring Data JPA** + **PostgreSQL 16**
- **Liquibase** — миграции БД
- **RabbitMQ** + **Spring Cloud Stream** — асинхронное взаимодействие между сервисами
- **Docker Compose** — локальная инфраструктура (БД, брокер, Catalog Service)
- **Lombok**, **Springdoc OpenAPI**

## Зачем это делать

- Поработать с распределённой архитектурой — два сервиса, брокер сообщений, асинхронные потоки
- Решать задачи, которые встречаются на реальных проектах: race conditions, гарантии доставки, кэширование, аудит
- Подготовиться к собеседованиям — задачи покрывают темы, про которые могут спрашивать

## Задачи

Каждая задача — самостоятельная фича или исправление, которое добавляется поверх существующего сервиса. Задачи нужно выполнять в порядке нумерации создавая новый бренч от предыдущего.

| #  | Тема | Что делать |
|----|------|------------|
| 01 | **Compensating Transaction** | Ввести промежуточный статус `CANCELLATION_PENDING` для безопасной отмены бронирования. Реализовать rollback при ошибке Catalog Service (DLQ). |
| 02 | **Endpoint статистики** | `GET /api/booking/statistics` — агрегации на стороне БД: общее количество, разбивка по статусам, топ-5 ресурсов. |
| 03 | **Race conditions и зависшие отмены** | Обработать гонку между отменой и подтверждением. Фоновый job для повторной отправки зависших отмен. |
| 04 | **Аудит-лог** | Таблица истории изменений статуса. Endpoint с пагинацией `GET /api/bookings/{id}/history`. |
| 05 | **Идемпотентность** | Таблица `processed_events` для защиты от повторной обработки сообщений из брокера. |
| 06 | **Domain Events** | Публикация `BookingStatusChangedEvent` в RabbitMQ при каждом изменении статуса. |
| 07 | **Transactional Outbox** | Сохранение событий в outbox-таблицу в одной транзакции с бизнес-данными. Фоновая отправка с retry. |
| 08 | **Оптимизация запросов** | Анализ и добавление индексов. Интеграционные тесты на Testcontainers для проверки через `pg_indexes`. |
| 09 | **Notification Service** | HTTP-клиент с Retry-паттерном к внешнему сервису уведомлений. Graceful degradation. WireMock для тестов. |
| 10 | **Кэширование (Caffeine)** | Spring Cache + Caffeine для статистики. Инвалидация при изменении данных. |

## Быстрый старт

### Повторная отправка отмен (задача 3)

Если подтверждение Catalog приходит в статусе `CANCELLATION_PENDING`, сервис принимает
`CONFIRMED`, очищает `previousStatus` и `commandSentAt` и пишет WARNING о гонке событий.

Фоновая проверка выбирает `CANCELLATION_PENDING`, где `commandSentAt` строго раньше
`now - timeout`, и повторно отправляет команду с прежним `catalogRequestId` и новым
идентификатором события. Настройки в `application.yml`:

```yaml
booking:
  cancellation-retry:
    timeout: PT5M
    fixed-delay: PT1M
```

`PT5M` означает пять минут ожидания ответа. `PT1M` — минуту между завершением
проверки и следующим запуском. Таймаут должен быть положительным.
Job не меняет статус или время отправки: просроченные отмены повторяются на каждом
запуске, пока обычный обработчик ответа или DLQ не завершит ожидание.
Ошибка отправки одной команды логируется и не мешает отправке остальных.

### История изменений бронирования (задача 4)

При создании и каждом изменении статуса сервис добавляет запись в
`booking_status_history`: ID бронирования, предыдущий и новый статусы, время UTC,
причину и инициатора. При создании предыдущий статус — `null`.
Старые записи не перезаписываются. Повторная отправка команды отмены без смены
статуса и проигнорированные события не добавляют историю.

Для создания инициатором служит переданный `userId`, для автоматических событий —
`"System"`. Учебное допущение: при пользовательской отмене используется `userId`
владельца бронирования, поскольку текущий API не передаёт личность вызывающего.
Это не проверка авторизации: в системе с аутентификацией инициатора следует брать
из данных текущего пользователя.

Изменение бронирования и запись истории выполняются в одной транзакции БД:
либо сохраняются оба изменения, либо оба откатываются. Это не делает отправку
сообщения в RabbitMQ атомарной с БД — для этого предназначена задача 7 (Outbox).
Таблицу, внешний ключ и индекс создаёт Liquibase, changeset `3`.

Пример чтения первой страницы:

```http
GET /api/bookings/42/history?page=0&size=10
```

- `page` — номер страницы с нуля, по умолчанию `0`.
- `size` — положительный размер страницы, по умолчанию `10`.
- Ответ содержит `content` с записями и метаданные страницы, включая
  `totalElements`, `totalPages`, `number`, `size`.
- Порядок фиксирован: `changedAt DESC`, затем `id DESC` при одинаковом времени.
- Для существующего бронирования без истории возвращается пустая страница.
  История бронирований, созданных до миграции, задним числом не восстанавливается.
- Некорректные параметры и отсутствие бронирования возвращают HTTP 400
  через существующую обработку ошибок проекта.

Проверка из корня проекта (Java 21 и Maven):

```bash
mvn clean verify
```

`BookingServiceTest` проверяет записи для переходов статуса и отсутствие записей
при отклонённых действиях. `BookingHistoryIntegrationTest` использует H2 в режиме
PostgreSQL, настоящий Liquibase и транзакционный сервис: проверяет миграцию,
внешний ключ, индекс, откат при ошибках, сортировку, пагинацию и HTTP-ответы.
В этих тестах отправитель сообщений заменён заглушкой; проверка на реальном
PostgreSQL и с живыми RabbitMQ/Catalog отдельно не выполняется.

### Запуск сервиса

```bash
# Клонировать репозиторий
git clone https://github.com/devdad-ru/booking-service-java.git
cd booking-service-java

# Поднять инфраструктуру
docker compose up -d

# Запустить сервис (из директории booking-service/)
./mvnw spring-boot:run -Dspring-boot.run.profiles=development
```

После запуска:
- Booking Service: `http://localhost:8001`
- Swagger UI: `http://localhost:8001/swagger-ui.html`
- RabbitMQ Management: `http://localhost:15672` (guest/guest)

## Как сдать задание

### 1. Сделайте форк

Перейдите в репозиторий [devdad-ru/booking-service-java](https://github.com/devdad-ru/booking-service-java) и нажмите кнопку **Fork** в правом верхнем углу.

### 2. Разрешите запуск GitHub Actions

В вашем форке перейдите во вкладку **Actions** и нажмите **I understand my workflows, go ahead and enable them**. Это необходимо для автоматической проверки PR.

### 3. Клонируйте свой форк

```bash
git clone https://github.com/<ваш-username>/booking-service-java.git
cd booking-service-java
```

### 4. Создайте ветку для задачи
Например: tasks/task1 (или task01)
Триггеру автопроверки важно корректное название ветки и номера задачи (task1 или task01) другие названия веток не затриггерят проверку.
(каждую последующую ветку с новой задачей нужно создавать от предыдущей ветки задачи: task1 от master, task2 от task1 и т.д.)
```bash
git checkout -b tasks/task1
```

### 5. Выполните задачу и зафиксируйте изменения

```bash
git add .
git commit -m "Решение задачи <номер>"
git push origin tasks/task1
```

### 6. Создайте Pull Request в своём форке

Откройте свой форк на GitHub и создайте **Pull Request** в ветку `master` **вашего форка** (не в родительский репозиторий).

> При создании PR убедитесь, что base repository — это **ваш форк**, а не `devdad-ru/booking-service-java`.

PR можно создать через GitHub в браузере или прямо из IDE, если в ней подключен ваш GitHub-аккаунт и есть функция создания Pull Request.

После создания PR автоматически запустится workflow, который отправит ваше решение на проверку.

### 7. Приложите ссылку на PR в ответ

Сразу после создания PR скопируйте ссылку на него и отправьте её в ответе на задание на платформе.

Пример ссылки:

```text
https://github.com/<ваш-username>/booking-service-java/pull/<номер-pr>
```

Важно: ссылку нужно отправить в течение **5 минут** после создания или обновления PR. Если ссылка не будет найдена в ответе на задание за это время, проверка не запустится.

Если вы не успели отправить ссылку вовремя, отправьте ссылку в ответе на задание и сделайте новый `push` в ту же ветку PR.

### 8. Если задание требует доработки

Не создавайте новый PR. Внесите правки в той же ветке, сделайте новый commit и `push`.

После этого нажмите кнопку "Редактировать" и "Отправить на проверку", чтобы запустить повторную проверку по уже вложенному PR.

## Архитектура

```
┌──────────┐      REST       ┌─────────────────┐     RabbitMQ     ┌─────────────────┐
│  Client  │ ──────────────> │ Booking Service  │ <─────────────> │ Catalog Service  │
└──────────┘                 │   (Java/Spring)  │                 │    (.NET/C#)     │
                             └────────┬─────────┘                 └────────┬─────────┘
                                      │                                    │
                                      v                                    v
                               ┌──────────────┐                    ┌──────────────┐
                               │ PostgreSQL    │                    │ PostgreSQL   │
                               │ (Booking DB)  │                    │ (Catalog DB) │
                               └──────────────┘                    └──────────────┘
```

Booking Service принимает запросы на бронирование, отправляет команды в Catalog Service через RabbitMQ и обрабатывает ответы (подтверждение/отказ). Catalog Service управляет доступностью ресурсов и поставляется как готовый Docker-образ — его код менять не нужно.
